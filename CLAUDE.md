## Project Overview

This is a B2B "송영" (shuttle/pickup) MaaS (Mobility-as-a-Service) platform for institutions requiring scheduled and on-demand transportation services using 5-15 passenger vehicles. The platform handles morning/evening fixed routes and dynamic temporary requests.

## Core Business Model

- **B2B Service**: Institutions (identified by business registration number) subscribe to shuttle services
- **Vehicle Capacity**: 5-15 passenger vehicles
- **Service Types**:
  - Morning shuttle: Multiple pickups → Single institution dropoff
  - Evening shuttle: Single institution pickup → Multiple dropoffs
  - Temporary/on-demand: Dynamic pickup/delivery requests

## System Architecture

### Cloud-Native Microservices Architecture (MSA)

The platform follows Domain-Driven Design (DDD) with these bounded contexts:

1. **Institution Context**: Institution management, B2B contracts, subscription plans, monthly billing
2. **Fleet Context**: Vehicle management (identified by last 4 digits of license plate), telematics integration, vehicle status
3. **Roster Context**: Weekly passenger manifests with boarding order, shuttle types (morning/evening/temporary), boarding/alighting status
4. **Route Context**: AI-based VRP (Vehicle Routing Problem) engine for optimal boarding sequence, real-time route recalculation, ETA computation
5. **User Context**: Authentication/authorization for institution admins, drivers, passengers/guardians

### Technology Stack Vision

**Backend**:
- Containerization: Docker with Kubernetes orchestration
- Event-Driven Architecture: Kafka or RabbitMQ for async service communication
- API Gateway: Apigee or AWS API Gateway
- Cloud Provider: GCP, AWS, or Azure managed services recommended

**Data Pipeline** (FMS - Fleet Management System):
- IoT Protocol: MQTT for vehicle telemetry
- Ingestion: AWS IoT Core or equivalent
- Streaming: AWS MSK (Managed Kafka) or equivalent
- Storage:
  - S3/Cloud Storage for raw data lake
  - DynamoDB/NoSQL for real-time vehicle state
  - Redis for cache and real-time dashboards

**Hardware**:
- Telemetry devices with OBD-II/CAN Bus access for collecting fuel efficiency, RPM, driving behavior, fault codes
- Optional: BLE beacons + LTE composite terminals for automatic passenger check-in

## AI Route Optimization Engine

### Core Problem: VRP-PDTW

The routing challenge is modeled as a Capacitated Vehicle Routing Problem with Pickup-Delivery and Time Windows (CVRP-PDTW):

- **Capacity constraint**: Vehicle passenger capacity (5-15 seats)
- **Time windows**: Institution arrival times, passenger pickup/dropoff preferences
- **Boarding order**: Generated by AI, not fixed routes

### Implementation Approach

- **Library**: Google OR-Tools for VRP solving
- **Modeling**:
  - Capacity dimension with vehicle max capacity
  - Pickup nodes: demand = +1 (add passenger)
  - Dropoff nodes: demand = -1 (remove passenger)
  - Constraint: cumulative load ≥ 0 (prevent phantom passengers)
- **Input**: Vehicle list (capacity, depot), passenger list (pickup/dropoff locations, time windows)
- **Output**: Optimized boarding sequence per vehicle, ETA for each stop

## Data Collection & GPS Logging

### Telemetry Requirements
- **GPS tracking**: High-precision location data
- **OBD-II/CAN Bus data**: Fuel level, RPM, speed, odometer, fault codes for B2B value differentiation
- **Driving behavior**: Harsh acceleration/braking, speeding, idle time

### GPS Distance Recording
- Collect GPS coordinates (lat/lon) during trips
- Use "Snap-to-Roads" API (Google Maps Roads API) to correct GPS noise
- Calculate actual driving distance along road network
- Store trip logs with timestamps for compliance (tax reporting) and billing

## Passenger Check-In Technology

| Method | Pros | Cons | Recommended Stage |
|--------|------|------|------------------|
| Manual driver check | No cost, immediate | Inaccurate, driver burden | MVP |
| QR code scan | Low cost, universal | Boarding delay, smartphone required | Stage 2 (adults) |
| NFC tag | Fast tap, no battery | Limited iPhone support, card/reader needed | Stage 2 (adults) |
| **BLE beacon + LTE terminal** | Automatic, no intervention, reliable LTE connectivity | Beacon battery management | **Stage 3 (recommended for children/elderly)** |

- Driver app: trip start/end, manual passenger check

### Stage 2 (Scaling & Optimization)
- AI VRP engine for automatic boarding sequence generation
- Basic BI dashboards in admin portal
- QR/NFC passenger check-in

### Stage 3 (Advanced MaaS - Differentiation)
- OBD-II/CAN Bus integration for advanced BI (driver behavior analysis, predictive maintenance)
- BLE beacon automatic check-in with safety alerts
- Demand-responsive temporary shuttle system

## Development Priorities

1. **AI Route Optimization**: The "manifest means boarding order" requirement is the most complex technical challenge - prioritize Google OR-Tools VRP integration early
2. **Telemetry Quality**: Choose OBD-II capable hardware from the start to enable future BI differentiation
3. **Data Pipeline Reliability**: Real-time GPS and event streaming (Kafka) are critical for fleet monitoring and passenger notifications
4. **OCR Integration**: Receipt OCR (NAVER CLOVA OCR, Kakao i OCR) for fuel/maintenance expense automation
5. **Geofencing**: Implement geofence-based arrival notifications for passenger peace of mind

## Key Business Differentiators

- **AI-optimized boarding sequence** (not fixed routes)
- **Advanced telematics BI**: fuel efficiency, driver safety scores, predictive maintenance
- **Automatic passenger tracking**: BLE beacons for guardian peace of mind
- **Transparent cost management**: OCR receipt processing, detailed mileage logs
- **Service Level Agreement (SLA) monitoring**: on-time performance tracking
