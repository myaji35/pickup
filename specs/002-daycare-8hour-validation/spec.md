# Feature Specification: 주간보호 8시간 케어 스케줄 검증

**Feature Branch**: `002-daycare-8hour-validation`
**Created**: 2025-11-18
**Status**: Draft
**Input**: User description: "주간보호기관의 8시간 케어 스케줄 관리 및 탑승/하차 시간 검증 기능"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 승객 탑승/하차 시간 입력 및 8시간 검증 (Priority: P1)

기관 관리자는 주간보호 서비스를 이용하는 승객의 희망 탑승 시간과 하차 시간을 입력할 수 있어야 하며, 시스템은 두 시간의 간격이 최소 8시간 이상인지 자동으로 검증해야 한다.

**Why this priority**: 재가장기요양기관의 주간보호 서비스는 법적으로 하루 8시간 케어를 제공해야 하므로, 탑승/하차 시간 간격 검증은 필수 기능이다. 규정 미준수 시 급여 심사에서 불이익을 받을 수 있다.

**Independent Test**: 관리자가 승객 "김영희"의 탑승 시간을 "08:00", 하차 시간을 "17:00"으로 입력하면 9시간 간격으로 검증 통과하고, 탑승 시간 "08:00", 하차 시간 "15:00"으로 입력하면 7시간 간격으로 경고 메시지가 표시되는지 확인하면 테스트 완료.

**Acceptance Scenarios**:

1. **Given** 기관 관리자가 주간보호 승객 등록 화면에 있는 상태, **When** 탑승 시간 "08:00", 하차 시간 "17:00"을 입력하고 저장, **Then** "케어 시간 간격: 9시간 (검증 통과)" 메시지가 표시되고 승객 정보가 저장된다.
2. **Given** 기관 관리자가 주간보호 승객 등록 화면에 있는 상태, **When** 탑승 시간 "08:00", 하차 시간 "15:00"을 입력하고 저장, **Then** "경고: 케어 시간 간격이 7시간으로 최소 8시간 요건을 충족하지 못합니다" 경고 메시지가 표시되고, "그래도 저장하시겠습니까?" 확인 메시지가 나타난다.
3. **Given** 기관 관리자가 하차 시간을 탑승 시간보다 이른 시간으로 입력, **When** 탑승 시간 "17:00", 하차 시간 "08:00"을 입력, **Then** "하차 시간은 탑승 시간 이후여야 합니다" 오류 메시지가 표시되고 저장이 거부된다.
4. **Given** 승객 "김영희"의 탑승/하차 시간이 이미 등록된 상태, **When** 관리자가 하차 시간을 "17:00"에서 "14:00"으로 수정 시도, **Then** "경고: 수정 후 케어 시간 간격이 6시간으로 최소 8시간 요건을 충족하지 못합니다" 경고 메시지가 표시된다.
5. **Given** 승객 "김영희"가 8시간 미만 경고를 받은 상태, **When** 관리자가 "그래도 저장" 선택, **Then** 승객 정보가 저장되고, 승객 목록에서 해당 승객 옆에 "케어 시간 부족" 빨간색 경고 아이콘이 표시된다.

### User Story 2 - 기관 유형별 케어 시간 규칙 설정 (Priority: P2)

시스템 관리자(또는 기관 관리자)는 기관 유형(주간보호, 단기보호, 일반 등)을 설정하고, 각 유형별 최소 케어 시간 규칙을 정의할 수 있어야 한다.

**Why this priority**: 기관 유형에 따라 최소 케어 시간이 다를 수 있으며(주간보호 8시간, 단기보호 24시간 등), 향후 확장성을 위해 규칙을 설정 가능하도록 해야 한다. 하지만 MVP에서는 주간보호 8시간 규칙만 하드코딩해도 되므로 P2.

**Independent Test**: 관리자가 "주간보호" 기관 유형을 생성하고 최소 케어 시간을 "8시간"으로 설정한 후, 승객 등록 시 해당 규칙이 적용되는지 확인하면 테스트 완료.

**Acceptance Scenarios**:

1. **Given** 시스템에 기관 유형이 설정되지 않은 상태, **When** "주간보호" 유형을 생성하고 최소 케어 시간 "8시간"을 설정, **Then** "기관 유형이 생성되었습니다" 메시지가 표시되고 기관 유형 목록에 "주간보호 (최소 8시간)"가 나타난다.
2. **Given** "주간보호" 기관 유형(8시간)과 "단기보호" 기관 유형(24시간)이 설정된 상태, **When** 기관 관리자가 자신의 기관 유형을 "주간보호"로 선택, **Then** "기관 유형이 적용되었습니다. 이후 승객 등록 시 8시간 케어 시간 검증이 적용됩니다" 메시지가 표시된다.
3. **Given** 기관이 "주간보호" 유형으로 설정된 상태, **When** 관리자가 기관 유형을 "일반"(케어 시간 제약 없음)으로 변경, **Then** "기관 유형이 변경되었습니다. 이후 승객 등록 시 케어 시간 검증이 적용되지 않습니다" 메시지가 표시된다.

### User Story 3 - 케어 시간 준수 현황 모니터링 및 리포트 (Priority: P3)

기관 관리자는 주간보호 승객들의 탑승/하차 시간 기록을 조회하고, 8시간 케어 준수 여부를 통계로 확인할 수 있어야 한다.

**Why this priority**: 모니터링 및 리포트 기능은 관리 효율성을 높이지만, 핵심 검증 기능이 먼저 구현되어야 하므로 우선순위가 낮다.

**Independent Test**: 관리자가 "케어 시간 준수 리포트" 화면에서 현재 등록된 승객들의 8시간 이상 케어 비율을 조회할 수 있으면 테스트 완료.

**Acceptance Scenarios**:

1. **Given** 주간보호 승객 10명이 등록되어 있고, 그 중 8명은 8시간 이상, 2명은 8시간 미만으로 설정된 상태, **When** "케어 시간 준수 리포트" 조회, **Then** "8시간 이상: 8명 (80%), 8시간 미만: 2명 (20%)" 통계가 표시된다.
2. **Given** 승객 "김영희"의 탑승/하차 시간 정보가 등록된 상태, **When** 승객별 상세 정보 조회, **Then** 탑승 시간, 하차 시간, 케어 시간 간격이 표시되고, 8시간 미만인 경우 빨간색으로 강조 표시된다.
3. **Given** 관리자가 리포트 화면에서 "8시간 미만만 보기" 필터 선택, **When** 필터 적용, **Then** 케어 시간 부족 승객 목록만 표시되고, 각 승객의 부족 시간(예: "6시간, 2시간 부족")이 함께 표시된다.

---

### Edge Cases

**시간 입력 및 검증 관련**:
- 탑승 시간과 하차 시간이 동일한 경우 어떻게 처리할 것인가? (예: 08:00 - 08:00) → 0시간으로 계산되어 8시간 미만 경고
- 자정을 넘어가는 경우 어떻게 처리할 것인가? (예: 23:00 탑승, 다음날 07:00 하차 = 8시간) → Out of Scope (Assumptions에 명시)
- 승객이 탑승 시간만 있고 하차 시간이 없는 경우 검증을 어떻게 처리할 것인가? → 두 시간 모두 입력되어야 검증 수행
- 분 단위 입력이 가능한가? (예: 08:30 - 16:45) → 가능함 (HH:MM 형식)

**기관 유형 및 규칙 관련**:
- 기관 유형이 설정되지 않은 경우 기본값은 무엇인가? → "일반"(케어 시간 제약 없음)으로 기본 설정
- 기관 유형을 변경하면 기존에 등록된 승객들의 케어 시간 검증 규칙도 소급 적용되는가? → 소급 적용되지 않음, 변경 이후 등록/수정되는 승객부터 새 규칙 적용
- 하나의 기관에 여러 유형이 혼재할 수 있는가? → 불가능, 하나의 기관은 하나의 유형만 가능 (Assumptions에 명시)

**데이터 정합성 관련**:
- 실제 탑승/하차 시간이 희망 시간과 다를 경우 어떻게 처리할 것인가? → Out of Scope (이 기능은 희망 시간만 다룸)
- 001번 기능에서 이미 등록된 승객에게 시간 정보를 추가할 때 기존 데이터는 어떻게 처리할 것인가? → 기존 승객은 시간 정보가 null이며, 관리자가 수정 시 입력 가능

## Requirements *(mandatory)*

### Functional Requirements

**승객 시간 정보 관리 요구사항**:

- **FR-001**: 시스템은 기관 관리자가 승객별 희망 탑승 시간을 입력할 수 있어야 하며, 시:분 형식(HH:MM)으로 입력받아야 한다.
- **FR-002**: 시스템은 기관 관리자가 승객별 희망 하차 시간을 입력할 수 있어야 하며, 시:분 형식(HH:MM)으로 입력받아야 한다.
- **FR-003**: 시스템은 탑승 시간과 하차 시간을 모두 입력받은 경우, 두 시간 간의 간격을 자동으로 계산해야 한다.
- **FR-004**: 시스템은 하차 시간이 탑승 시간보다 이른 경우 오류 메시지를 표시하고 저장을 거부해야 한다.
- **FR-005**: 시스템은 탑승 시간과 하차 시간이 모두 입력되어야 케어 시간 검증을 수행하며, 하나만 입력된 경우 검증을 건너뛰어야 한다.

**케어 시간 검증 요구사항**:

- **FR-006**: 시스템은 기관이 "주간보호" 유형으로 설정된 경우, 탑승-하차 시간 간격이 8시간 이상인지 자동으로 검증해야 한다.
- **FR-007**: 시스템은 케어 시간 간격이 8시간 미만인 경우 경고 메시지를 표시해야 하며, 메시지에는 실제 간격(예: "7시간")과 최소 요구 시간(8시간)을 포함해야 한다.
- **FR-008**: 시스템은 8시간 미만 경고 발생 시, 관리자가 "그래도 저장" 또는 "취소" 중 선택할 수 있도록 해야 한다.
- **FR-009**: 시스템은 "그래도 저장"을 선택한 경우, 승객 정보를 저장하되 "케어 시간 부족" 플래그를 함께 저장해야 한다.
- **FR-010**: 시스템은 승객 정보 수정 시에도 탑승/하차 시간이 변경되면 케어 시간 검증을 재수행해야 한다.

**기관 유형 및 규칙 설정 요구사항**:

- **FR-011**: 시스템은 기관 유형(주간보호, 단기보호, 일반 등)을 관리할 수 있어야 하며, 각 유형별 최소 케어 시간(시간 단위)을 설정할 수 있어야 한다.
- **FR-012**: 시스템은 기관 관리자가 자신의 기관에 기관 유형을 선택하여 적용할 수 있어야 한다.
- **FR-013**: 시스템은 기관 유형이 "일반"(케어 시간 제약 없음)으로 설정된 경우, 케어 시간 검증을 수행하지 않아야 한다.
- **FR-014**: 시스템은 기관 유형 변경 시, 변경 사실을 관리자에게 알리고 "이후 등록/수정되는 승객부터 새 규칙이 적용됨"을 명시해야 한다.
- **FR-015**: 시스템은 기관 유형이 설정되지 않은 경우, 기본값으로 "일반" 유형을 적용해야 한다.

**케어 시간 모니터링 요구사항**:

- **FR-016**: 시스템은 승객 목록에서 케어 시간 부족 플래그가 있는 승객을 시각적으로 구분하여 표시해야 한다(예: 빨간색 경고 아이콘).
- **FR-017**: 시스템은 기관 관리자가 케어 시간 준수 현황을 조회할 수 있어야 하며, 8시간 이상/미만 승객 수와 비율(%)을 표시해야 한다.
- **FR-018**: 시스템은 승객별 상세 케어 시간 정보를 조회할 수 있어야 하며, 탑승 시간, 하차 시간, 케어 간격을 표시해야 한다.
- **FR-019**: 시스템은 케어 시간 부족 승객만 필터링하여 조회할 수 있는 기능을 제공해야 한다.

**데이터 연동 요구사항**:

- **FR-020**: 시스템은 001번 기능(차량/승객 관리)에서 등록된 승객 정보에 탑승/하차 시간 정보를 추가할 수 있어야 한다.
- **FR-021**: 시스템은 승객 정보 조회 시 기본 정보(이름, 연락처 등)와 함께 탑승/하차 시간 정보를 통합하여 표시해야 한다.
- **FR-022**: 시스템은 001번 기능에서 이미 등록된 승객의 경우, 탑승/하차 시간이 null(미입력) 상태로 처리되어야 하며, 관리자가 수정 시 입력할 수 있어야 한다.

### Key Entities

- **승객 스케줄 (Passenger Schedule)**: 승객의 탑승/하차 시간 정보를 나타낸다. 주요 속성: 승객 ID(001번 기능과 연동), 희망 탑승 시간, 희망 하차 시간, 케어 시간 간격(계산값), 케어 시간 부족 플래그, 등록일시, 수정일시.
- **기관 유형 (Institution Type)**: 기관의 서비스 유형을 나타낸다. 주요 속성: 유형 코드(고유 식별자), 유형명(주간보호, 단기보호, 일반), 최소 케어 시간(시간 단위, null이면 제약 없음), 설명.
- **기관 유형 설정 (Institution Type Configuration)**: 기관과 기관 유형의 연결 관계를 나타낸다. 주요 속성: 기관 ID(001번 기능의 Institution 엔티티와 연동), 기관 유형 코드, 적용 시작일시.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 기관 관리자가 승객 1명의 탑승/하차 시간을 입력하고 8시간 검증을 완료하는 데 1분 이내 소요된다.
- **SC-002**: 탑승 시간 입력 후 하차 시간 입력 시, 케어 시간 간격이 실시간으로 계산되어 화면에 표시된다(1초 이내).
- **SC-003**: 8시간 미만 입력 시, 즉시 경고 메시지가 표시되어 관리자가 즉시 인지할 수 있다.
- **SC-004**: 케어 시간 준수 현황 리포트 조회 시, 승객 100명 기준 3초 이내에 통계가 표시된다.
- **SC-005**: 8시간 검증 기능 도입 후, 케어 시간 부족 승객의 사전 발견율이 100%에 도달한다(입력 시점에 즉시 경고).
- **SC-006**: 관리자의 95% 이상이 "케어 시간 검증 기능이 규정 준수에 도움이 된다"고 평가한다.
- **SC-007**: 케어 시간 부족 승객 비율이 리포트에서 한눈에 파악 가능하다(백분율 및 시각적 표시 활용).

## Assumptions

- 탑승/하차 시간은 희망 시간(예정 시간)으로, 실제 운행 시 기록되는 실제 시간과는 구분된다. (실제 시간 기록은 별도 기능)
- 하루는 24시간으로 가정하며, 자정을 넘어가는 케어 시간(예: 23:00 탑승 - 다음날 07:00 하차)은 이 기능 범위에 포함되지 않는다.
- 시간 입력은 분 단위까지 가능하다(HH:MM 형식, 예: 08:30).
- 주간보호 기관의 최소 케어 시간은 8시간으로 고정되어 있다. (향후 설정으로 변경 가능하도록 확장 가능)
- 하나의 기관은 하나의 기관 유형만 가질 수 있다.
- 기관 유형 변경 시 기존 승객 데이터는 소급 적용되지 않으며, 변경 이후 등록/수정되는 승객부터 새 규칙이 적용된다.
- 001번 기능(차량/승객 관리)의 승객 엔티티가 이미 구현되어 있다고 가정하며, 이 기능은 승객 엔티티를 확장한다.
- 기관 유형이 설정되지 않은 경우 기본값은 "일반"(케어 시간 제약 없음)이다.
- 탑승 시간 또는 하차 시간 중 하나만 입력된 경우, 케어 시간 검증을 수행하지 않는다.

## Scope Boundaries

**포함되는 것 (In Scope)**:
- 승객별 희망 탑승/하차 시간 입력
- 탑승-하차 시간 간격 자동 계산
- 주간보호 기관의 8시간 최소 케어 시간 검증
- 8시간 미만 시 경고 메시지 표시 및 "그래도 저장" 옵션
- 기관 유형 설정 및 관리 (주간보호, 일반 등)
- 기관 유형별 최소 케어 시간 규칙 정의
- 케어 시간 준수 현황 모니터링 및 리포트
- 케어 시간 부족 승객 시각적 구분 표시
- 001번 기능(승객 관리)과의 데이터 연동

**포함되지 않는 것 (Out of Scope)**:
- 실제 탑승/하차 시간 기록 (운전자 앱 기능)
- 자정을 넘어가는 케어 시간 계산 (24시간 초과 시나리오)
- 일자별 실제 운행 기록 기반 케어 시간 추적
- AI 기반 최적 탑승/하차 시간 추천
- 케어 시간 기반 요금 자동 계산
- 승객별 케어 시간 알림/푸시 기능
- 외부 요양급여 심사 시스템과의 연동
- 주별/월별 케어 시간 누적 통계 (현재 기능은 승객별 설정값 기준 통계만 제공)

## Dependencies

- **001번 기능 (차량/승객/그룹 관리)**: 승객 엔티티와 기관 엔티티가 이미 구현되어 있어야 하며, 이 기능은 해당 엔티티들에 시간 정보 및 유형 정보를 추가함
- 기관 인증/인가 시스템: 관리자가 자신의 기관 유형 설정에만 접근할 수 있도록 제어 필요
- 날짜/시간 처리: 시간 간격 계산을 정확하게 수행하기 위한 기능 필요 (시간 차이 계산)
